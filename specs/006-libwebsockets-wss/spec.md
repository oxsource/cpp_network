## Clarifications

### Session 2026-08-27

- Q: 连接通道是否仅限加密的 wss？ → A: 也需要兼容明文 ws；两种通道均须支持。
- Q: 双通道兼容后，模块目录与公开类型如何命名？ → A: 回归 websocket 语义——目录 `src/websocket`、公开类型 `WebSocket`（初始输入的"简化为 wss"命名作废）。
- Q: 对 `ws://` 明文连接携带 TLS 配置时的行为？ → A: 静默忽略——TLS 配置仅对加密通道生效，明文连接照常建立。
- Q: 接收侧如何呈现对端发起的关闭？ → A: 带详情失败——关闭后的接收调用返回明确的"连接已关闭"错误，其中可读取对端的关闭码与原因短文。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立 WebSocket 连接（ws 与 wss 双通道） (Priority: P1)

应用开发者通过本库与一个 WebSocket 服务端建立连接：给定 `wss://`（加密）或 `ws://`（明文）地址与网络配置（超时、TLS 配置），调用方线程阻塞至握手完成；成功后获得可用的连接对象，失败则得到携带明确错误码的结果（无法解析的地址、证书校验失败、握手被拒等）。

加密通道（wss）的 TLS 行为与 HTTP 客户端完全一致：默认拒绝自签名/不可信证书；可通过既有 TLS 配置注入信任锚（文件或内存 PEM）；也可显式选择跳过校验（测试用途）。明文通道（ws）不涉及 TLS。所有受支持平台行为逐项一致。

**Why this priority**: 连接是一切消息交互的前提；单此一个故事即可独立交付"库具备 WebSocket 能力（含安全与非安全通道）"的最小可用价值。

**Independent Test**: 对本地或公网回声服务（加密与非加密各一）发起连接并观察结果；不依赖任何后续故事即可验证。

**Acceptance Scenarios**:

1. **Given** 一个证书受信的安全 WebSocket 服务端，**When** 以默认配置连接其 `wss://` 地址，**Then** 连接成功且处于可收发状态。
2. **Given** 一个明文 WebSocket 回声服务端，**When** 以默认配置连接其 `ws://` 地址，**Then** 连接成功且处于可收发状态。
3. **Given** 一个自签名证书的服务端，**When** 以默认配置连接其 `wss://` 地址，**Then** 连接被拒绝并返回证书校验失败的错误码。
4. **Given** 同一自签名服务端的 CA 已通过内存 PEM 注入，**When** 再次连接，**Then** 连接成功。
5. **Given** 一个既非 `ws://` 也非 `wss://` 的地址，**When** 发起连接，**Then** 调用快速失败并返回无效参数错误，不产生任何网络请求。
6. **Given** 一个不可达的地址，**When** 以 N 秒超时连接，**Then** 至多等待 N 秒后返回连接失败错误。

---

### User Story 2 - 消息收发（文本与二进制） (Priority: P1)

连接建立后，调用方以阻塞方式发送与接收完整消息：发送文本或二进制载荷，随后能按序接收对端发来的消息。发送期间的长消息对调用方透明——底层分段不影响上层一次发送/一次接收即得到完整消息语义。对端探活帧由库自动应答，不作为消息暴露给调用方。

**Why this priority**: 收发是 WebSocket 的核心价值；与 US1 合成最小完整闭环（连接+回声），构成可演示的 MVP。

**Independent Test**: 连接安全回声服务，发送文本与二进制各一条，逐一收到原样回声。

**Acceptance Scenarios**:

1. **Given** 已连接的会话，**When** 发送一条文本消息，**Then** Receive 返回同内容文本消息。
2. **Given** 已连接的会话，**When** 发送一条二进制消息，**Then** Receive 返回同内容二进制消息且类型标记正确。
3. **Given** 服务端一次逻辑消息被拆分为多个底层分段发送，**When** 调用 Receive，**Then** 库完成透明重组，一次返回完整消息。
4. **Given** 已连接的会话空闲且服务端周期性发送探活帧，**When** 后续 Receive 一条真实消息，**Then** 探活帧被自动处理，未混入消息流。

---

### User Story 3 - 关闭与状态收敛 (Priority: P2)

任一方均可终结会话：调用方主动关闭时给出标准关闭码与原因，库执行完整的双向关闭握手（含限时等待对端确认）；对端先关闭或异常断线时，后续发送/接收调用快速返回明确的"连接已关闭"类错误而非挂起。调用方在任意时刻查询连接是否可用都得到即时答案。

**Why this priority**: 无干净关闭会造成资源泄漏与服务端悬置会话，但其价值建立在收发之上。

**Independent Test**: 与回声服务完成"连接—关闭"全程；再验证"服务端先行断开"后调用的快速失败行为。

**Acceptance Scenarios**:

1. **Given** 已连接的会话，**When** 以正常关闭码主动关闭，**Then** 关闭在时限内完成且此后 Send/Receive 快速返回已关闭错误。
2. **Given** 服务端主动断开会话，**When** 调用方随后 Send 或 Receive，**Then** 快速返回明确的连接已关闭错误；经 Receive 可读取对端关闭码与原因短文（若服务端提供）。
3. **Given** 已连接的会话，**When** 重复调用关闭，**Then** 第二次及以后的调用幂等返回成功或已关闭，不产生异常。

---

### User Story 4 - 平台一致性与依赖治理 (Priority: P3)

新增能力在全部受支持平台（桌面与移动）上行为一致，并且新引入的第三方协议组件纳入既有的单一事实源依赖治理：版本锁定、升级演练流程覆盖、符号与构建约定沿用现有后端策略。占位的旧版模块命名随本特性一并收敛简化。

**Why this priority**: 属于横切保障项，不阻塞功能价值交付但决定可维护性。

**Independent Test**: 依赖版本更新演练 + 各平台（至少 macOS 真机与 Android 真机）运行同一套用例全绿。

**Acceptance Scenarios**:

1. **Given** 触发一次第三方组件版本升级演练，**When** 执行既有的一键验证流程，**Then** 全部用例通过且总耗时不超过既定演练预算。
2. **Given** 同一套 WSS 用例，**When** 分别在两个平台的真机/宿主上执行，**Then** 场景判定结果完全一致。

### Edge Cases

- 两种通道（明文与加密）均受支持；加密通道的安全基线（默认拒自签）不因明文通道的存在而松动。
- 对明文连接附加 TLS 配置：静默忽略（FR-001），文档须明确声明该语义，避免"以为加密了"的误解。
- TLS 配置互斥/配对规则非法（同时给文件锚与内存锚、只给客户端证书缺私钥等）：复用既有校验语义，连接前快速失败。
- 极大消息（数 MB）：调用方无需感知内部分段与缓冲管理，Send/Receive 仍满足一次性完整消息语义。
- 零长度消息：允许发送（协议层面合法的空载荷帧）；接收侧不凭空合成零长度消息，仅在确有此类入站帧时如实传递。
- 握手中途对端断开：返回连接失败而非无限等待。
- 未连接即调用 Send/Receive/Close：快速返回状态错误。
- 同一线程模型约束下并发调用同一连接的收发：v1 不承诺多线程安全，文档声明单线程使用边界（调用方自行串行化）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接受加密（`wss://`）与明文（`ws://`）两类 WebSocket 连接；其余协议前缀 MUST 在发起任何网络活动前被拒绝。TLS 配置仅对加密通道生效：对明文通道附加的 TLS 配置 MUST 被静默忽略（连接照常建立）。
- **FR-002**: 系统 MUST 以阻塞同步形态提供连接、发送、接收、关闭四个操作，全部经由统一的错误/结果类型返回，无回调、无事件循环暴露。
- **FR-003**: TLS 行为 MUST 与 HTTP 客户端共用同一套 TLS 配置语义与判定规则（信任锚注入、跳过校验模式、配置合法性校验），且驱动自同一个源码构建的 TLS 后端——禁止引入第二套 TLS 实现。
- **FR-004**: 新增协议组件 MUST 经由单一事实源注册表锁版本集成，随平台统一构建（静态链接、目标级符号隐藏约定同既有三方组件）。
- **FR-005**: 消息模型 MUST 支持文本与二进制两类载荷，并以完整消息为原子单位收发；底层分段/重组 MUST 对调用方透明。
- **FR-006**: 探活帧 MUST 由库自动应答，MUST 不出现在接收消息流中。
- **FR-007**: 关闭 MUST 支持标准关闭码与原因短文，并执行限时双向关闭握手；主动关闭后的再次操作 MUST 幂等不异常。
- **FR-008**: 会话状态 MUST 可即时查询（可用/不可用）；任何在不可用状态下的收发关尝试 MUST 快速返回明确的状态类错误，不得挂起。
- **FR-009**: 连接、关闭 MUST 受统一超时配置约束（连接超时、关闭等待上限）。
- **FR-010**: 原 WebSocket 占位模块 MUST 被真实实现取代；模块目录与公开类型采用 websocket 语汇（`src/websocket`、类型 `WebSocket`），以同时覆盖明文与加密双通道。
- **FR-011**: 新增能力的引入 MUST 不破坏既有 HTTP(S) 用例数量与断言（回归闸延续）。
- **FR-012**: 压缩扩展（permessage-deflate）与自动重连不在本期范围（显式排除）。

### Key Entities *(include if feature involves data)*

- **WebSocket 连接**: 会话句柄；持有状态（连接中/开放/关闭中/已关闭）、所绑定的目标地址与生效配置（加密通道含 TLS 配置）；生命周期内绑定单一目标。
- **Ws 消息**: 原始字节载荷 + 文本/二进制类型标记。
- **关闭信息**: 标准关闭码 + 原因短文；双向暴露——主动关闭时由调用方提供，对端发起关闭后经接收侧的错误详情可读取。
- **网络配置（复用）**: 超时集合与 TLS 配置对象；TLS 配置对象按既有规则校验后应用于 WSS 握手。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 与安全回声服务的"连接—文本回声—二进制回声—关闭"全流程在本机环回下 95 分位不超过 100ms（不含服务端排队）。
- **SC-002**: 自签名拒绝/注入通过这对安全基线场景在全部受支持平台上的判定结果逐项一致（0 分歧）。
- **SC-003**: 引入本特性后，既有 HTTP(S) 全量用例保持全部通过且断言零删改。
- **SC-004**: 含新组件在内的依赖版本升级演练（清缓存重建 + 全量回归）总耗时不超过 30 分钟。
- **SC-005**: WSS 场景用例可以通过一条命令在任一接入的真机上完成执行并给出 7 项以上场景判定。

## Assumptions

- 仅做客户端；不做服务端监听。
- 同步阻塞调用模型沿袭 003 定型（JS WebSocket 类比的同步对应表继续适用）；异步包装留给上层。
- 通道支持范围：加密（wss）与明文（ws）双通道均需兼容（2026-08-27 澄清，覆盖初始输入"只是wss"）；加密通道默认仍拒自签，不因明文可用而松动。
- 自动重连不在本期范围（001 草案中的可配置重连延后；调用方需要时可自行外层重试）。
- 探活/心跳的超时间隔沿用所选协议组件的合理默认，暂不单独暴露配置项。
- 压缩扩展（permessage-deflate）延后。
- 单连接单线程使用（Send/Receive 不承诺跨线程并发安全）；多连接互不影响。
- 新组件与既有 HTTP 共存于同一进程/同一构建图，但各自独立驱动传输层内部事件（不强求共享轮询引擎）。
