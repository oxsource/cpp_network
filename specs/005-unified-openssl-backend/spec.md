# Feature Specification: 全平台统一 OpenSSL TLS 后端

**Feature Branch**: `005-unified-openssl-backend`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "按照上述讨论的方案制定提案"（host 平台默认切换至与 Android 相同的源码构建 OpenSSL+libcurl，直接翻转默认值，移除系统 libcurl 依赖路径；覆盖 macOS arm64 与 Linux x86_64/aarch64；共享库严格隐藏第三方符号）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 宿主平台与 Android 行为完全一致 (Priority: P1)

使用本网络库的 macOS/Linux 开发者发现：同一份应用代码在所有支持平台上产生的 TLS/证书行为完全一致——证书校验语义、内存 PEM 注入路径、SNI 处理不再因操作系统不同而出现差异。此前 macOS 上"证书内容注入需经临时文件兜底"的平台怪癖消失，所有证书能力走统一通道。

**Why this priority**: 本特性的核心价值——跨平台一致性；S2/S3 类能力此前在不同平台上验证路径不同，收敛后测试与应用行为均可逐字节比对。

**Independent Test**: 在 macOS 与 Android 真机各运行一次既有 e2e 检查程序，逐场景 diff 结果；全部一致且全绿即成立。

**Acceptance Scenarios**:

1. **Given** 任一支持平台（macOS/Android）上的检查程序，**When** 执行完整的既有场景集合（自签拒绝、文件 CA、内存 CA、mTLS 双向、跳过校验、HTTP 基线），**Then** 结果清单与另一平台逐项相同。
2. **Given** macOS 环境，**When** 使用内存文本形式注入证书，**Then** 成功路径不经过任何临时文件落盘（行为迁移至运行时内存注入能力），失败路径错误信息与其他平台一致。
3. **Given** Linux 构建产物，**When** 开发者审阅构建输出，**Then** TLS 能力存在且与文档声明的行为契约相符（本故事内以构建成功为验收，运行级验证标记为待后续设备/宿主执行）。

---

### User Story 2 - 安全补丁职责的显式承接 (Priority: P1)

当底层加密组件发布安全公告时，项目维护者能够通过更新一处版本锁定完成全平台升级，且升级后全平台回归一次性通过。运维/安全团队可以在仓库中找到一个明确的位置回答"当前所有平台用的是哪个版本的加密组件？上一版是什么时候换的？"。

**Why this priority**: 统一后端把补丁职责从操作系统转移到本项目——必须同时交付"可低成本升级"的能力才构成完整决策。

**Independent Test**: 模拟一次版本号变更提交，确认无需修改任何构建逻辑之外的内容即可全平台重建并通过回归。

**Acceptance Scenarios**:

1. **Given** 仓库中的版本锁定文件，**When** 维护者仅修改其中的版本标识与校验和并重新构建，**Then** 所有目标平台的产物基于新版本生成。
2. **Given** 任一历史标签，**When** 运维人员查找当时使用的加密组件版本，**Then** 可从单一事实源文件直接读出。

---

### User Story 3 - 移除对宿主系统传输层的隐性依赖 (Priority: P2)

宿主机器不再要求安装特定版本的系统传输层库：全新的 Linux 发行版或最小化 macOS 环境上，克隆仓库即可完成完整构建与运行验证；此前"用户机器 libcurl 版本差异导致行为漂移"一类的问题被结构性消除。诊断时出现的传输层相关报告可确定性复现。

**Why this priority**: 显著改善可移植性与可重现性，但依赖 US1 的能力通道先建立。

**Independent Test**: 在无预装传输层开发包的环境中执行标准构建与演示程序运行成功。

**Acceptance Scenarios**:

1. **Given** 未安装任何系统级传输层开发包的最小环境，**When** 执行标准构建，**Then** 构建成功（不因缺少系统组件而失败）。
2. **Given** 同一仓库与配置，**When** 分别在两台不同 OS 版本的宿主上构建并运行演示程序，**Then** 输出结果一致。

---

### User Story 4 - 第三方符号严格隐藏 (Priority: P2)

将本库编译为动态链接形态分发给第三方应用时，第三方符号（加密组件、传输层）不出现在导出表中——应用只能看到本库公开 API 符号，杜绝下游与自身依赖版本冲突或误用内部符号的可能。

**Why this priority**: 质量属性要求（供应链与集成卫生），随 US1 交付一并验证。

**Independent Test**: 对共享形态产物执行符号表审计，除公开 API 外零第三方符号命中即通过。

**Acceptance Scenarios**:

1. **Given** 共享形态产物，**When** 审计其导出符号表，**Then** 加密组件与传输层的实现符号均不可见。
2. **Given** 两个分别使用不同版本加密组件的应用同时链接本共享库，**When** 各自独立运行，**Then** 无符号冲突。

### Edge Cases

- 宿主编译器工具链中混入非系统默认归档器导致静态库格式不被链接器接受——构建脚本须显式选择归档器并对异常格式给出可直接行动的错误。
- 极小化 Linux 环境缺少某些常用命令行工具时，构建前置检查应精确指出缺失项而非半途报模糊错误。
- 应用同时链接本库与另一个携带同名第三方符号的库——依靠符号隐藏策略在链接期自然消解；若仍冲突，文档需说明规避途径。
- 升级版本锁定后某个平台构建失败而其余成功——失败应立即中止整体流程并明确指出失败平台与日志位置，禁止静默产出部分平台的新版本混合产物。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有受支持平台 MUST 使用同一套源码构建的加密与传输层组件（同一锁定版本），替代宿主系统提供的对应库。
- **FR-002**: 宿主平台（macOS、Linux x86_64/aarch64）MUST 通过既有单一入口构建目标获得包含新后端的全部产物，命令用法不变。
- **FR-003**: 系统提供库的链接路径 MUST 从构建图中移除（Android 分支已移除；本次扩展至其余平台），不留隐式回退。
- **FR-004**: 版本锁定的变更 MUST 仅需修改单一事实源文件；升级流程有文档化的步骤说明。
- **FR-005**: 传输层能力中的内存形态证书注入 MUST 在所有平台经由统一的运行时内存通道生效，消除平台特例分支。
- **FR-006**: 动态链接形态的库产物 MUST 隐藏全部第三方实现符号，仅暴露本库公开 API 符号。
- **FR-007**: 跨平台构建矩阵 MUST 更新为每个平台明确的验证等级标注（本机实测 / 构建级验证 / 待验证），禁止未验证状态下宣称通过。
- **FR-008**: 架构决策记录 MUST 修订为"全平台源码构建统一后端"，包含推翻先前"跟随平台"决策的理由、成本声明（含安全公告跟进责任转移）与遗留边界（如 Windows 仍排除）。
- **FR-009**: 既有 e2e 检查程序与测试资产 MUST 保持向后兼容：场景定义、退出码协议、资产根目录覆写点不变。

### Key Entities

延续 specs/004 定义的工作对象模型，本特性新增/修订：

- **BuildArtifact.config** 增加宿主分支取值：macOS/Linux 下同样由源码构建产物组成（此前仅 Android）。
- **TLSCapabilityMatrix**（新增，纯文档性实体）：平台 × 后端 × 信任锚来源 × 验证等级的四元清单，作为文档矩阵的唯一事实源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: macOS 与 Android 上既有的全量场景集合（7 项本地 + 3 项外网）逐项结果一致且全部通过。
- **SC-002**: 版本锁定变更 → 全平台重建 → 回归通过的完整升级演练在 30 分钟内完成（不含首次源码下载）。
- **SC-003**: 全部 gtest 测试套件在翻转后保持通过，数量不减、断言不改。
- **SC-004**: 共享形态产物的导出符号审计中，第三方实现符号命中数为 0。
- **SC-005**: 最小化环境（无系统传输层开发包）的标准构建成功率 100%，且缺失组件类错误的排查指引能在一分钟内定位到具体缺失项。

## Assumptions

- Windows 平台维持排除于 v1 验收范围（沿用既有架构边界），后续单独立项评估。
- 三方组件继续沿用现锁定版本（加密组件 3.x LTS 当前 pin、传输层 8.7.1 当前 pin）；如需同步升级另行任务处理。
- Linux 平台的运行级验证需要对应的宿主机器；无法在本机执行的部分按矩阵约定的"构建级验证"等级交付并在文档明示，不视为缺陷隐瞒。
- 符号隐藏采用对象层可见性控制 + 关闭三方符号再导出的组合手段，不引入独立的链接器脚本维护面。
- 内存证书注入通道在 iOS/WebAssembly 等未列平台上的表现不在讨论范围内。


> **修订（2026-08-27，Phase 5 实施期用户决策）**：US4 符号严格隐藏降级为"发现与记录"。技术根因：现行 Apple clang 17 / macOS 26 工具链在对象文件层不再体现 visibility("hidden")（显式 attribute 同样失效），可靠收口需迁移到链接期白名单或新增 C API 门面——超出本特性范围。第三方符号管理将在后续独立的 C API 设计任务中处理；本特性的共享库交付物在导出表含三方实现符号的现状下如实发布，并在 evidence/symbol-audit-macos.md 留档根因分析。
