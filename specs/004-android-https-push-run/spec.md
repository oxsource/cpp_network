# Feature Specification: Android HTTPS 支持与一键设备部署运行

**Feature Branch**: `004-android-https-push-run`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "设计实现支持在android上也支持https，同步支持make push&run等"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Android 设备上发起并验证 HTTPS 请求 (Priority: P1)

使用本网络库的 Android 应用开发者在真机或模拟器上，通过既有的公共接口发起 HTTPS 请求：默认开启证书校验，注入自定义 CA（内存 PEM 或文件路径）后可访问自签证书服务器，客户端证书（mTLS）与跳过校验行为与桌面平台一致。应用代码无需为 Android 做任何修改或条件编译。

**Why this priority**: 这是本特性的核心价值——库在各平台上能力对齐；没有它，Android 集成无从谈起。

**Independent Test**: 在连接的 Android 设备上运行一个使用该库的最小程序，分别验证：自签证书默认被拒、注入 CA 后成功、mTLS 成功。三项均通过即成立。

**Acceptance Scenarios**:

1. **Given** 一台安装了使用本库应用的 Android 设备与一个本地自签 HTTPS 测试服务（经端口反向转发可达），**When** 应用以默认配置请求该服务，**Then** 请求失败且错误类型为证书校验失败（与其他平台一致）。
2. **Given** 同上环境，**When** 应用注入测试服务的 CA 证书后再次请求，**Then** 请求成功并返回预期内容。
3. **Given** 服务要求客户端证书，**When** 应用提供正确的客户端证书与私钥，**Then** 请求成功；不提供时失败。
4. **Given** 应用显式开启"跳过校验"，**When** 访问自签服务，**Then** 请求成功。

---

### User Story 2 - 开发者一条命令完成 Android 构建产物 (Priority: P1)

Android 应用开发者拉取仓库后，无需手工安装额外依赖或研究构建脚本，执行约定的构建命令即可得到面向 Android 的库产物（以及可直接在设备上运行的测试/演示程序），构建过程自动化：所需第三方组件按需获取或编译，产物按目标架构放置于约定输出目录。既有五平台验收矩阵中 Android 分支由"待验证"转为"实测通过"。

**Why this priority**: 与 US1 并列的核心交付——不可复现的构建等于不可用。

**Independent Test**: 在干净环境（无缓存目录）执行 Android 构建命令，确认退出码为零、产出物存在且可在模拟器上加载运行。

**Acceptance Scenarios**:

1. **Given** 全新克隆的仓库与已安装的基础开发工具链及 Android 平台工具，**When** 开发者执行 Android 构建命令，**Then** 构建成功并在约定位置产出库文件与设备端测试/演示程序。
2. **Given** 已完成过一次构建的环境，**When** 再次执行相同命令，**Then** 增量构建完成且耗时明显低于首次构建。

---

### User Story 3 - make push&run 一键部署到设备执行 (Priority: P2)

C++ 网络库开发者日常验证时，执行约定的 `push` 目标即可把设备端程序推送到当前连接的 Android 设备，执行约定的 `run` 目标即可远程启动它并把输出实时回传到本机终端；一次完整推送加执行的反馈时间足够短，可作为日常回归手段。未连接设备或有多个设备时的行为清晰、报错友好。

**Why this priority**: 显著改善日常迭代效率，但依赖 US1/US2 先成立。

**Independent Test**: 连接一台设备后依次执行 `push` 与 `run`，观察程序在设备上执行且结果回显；断开设备再执行应得到明确错误提示而非卡死。

**Acceptance Scenarios**:

1. **Given** 已连接一台授权的 Android 设备并已完成 US2 构建，**When** 开发者执行推送目标，**Then** 产物被复制到设备的约定目录。
2. **Given** 推送完成，**When** 执行运行目标，**Then** 设备上的程序被执行，其标准输出/错误实时显示在本机终端，进程结束后本机收到对应退出状态。
3. **Given** 未连接任何设备，**When** 执行推送或运行目标，**Then** 命令立即失败并提示如何排查（检查连接与授权）。
4. **Given** 连接了多台设备，**When** 开发者通过参数或环境变量指定目标设备序号执行，**Then** 操作仅作用于指定设备；未指定时给出设备列表提示并终止。

---

### User Story 4 - 无根权限与环境自适应的可移植性保障 (Priority: P3)

设备端程序不以 root 权限运行、不修改系统分区即可工作；所需的全部动态组件随产物一起被推送或在运行时从应用私有目录加载。换一台新的 Android 设备（不同厂商）时无需人工干预同样可跑通 US3 的流程。

**Why this priority**: 是质量属性要求而非新功能，故置于 P3，但缺少它会限制适用面。

**Independent Test**: 在一台未做任何定制的新设备上重复 US3 流程一次通过。

**Acceptance Scenarios**:

1. **Given** 未做任何特殊设置的普通消费级设备，**When** 完成 push & run 流程，**Then** 全程无 root 权限提示且执行成功。
2. **Given** 不同品牌的两台设备，**When** 分别执行同一套命令，**Then** 结果一致。

### Edge Cases

- 设备屏幕锁定/休眠导致临时无法执行时，工具链应给出明确等待或失败提示，而不是长时间静默挂起。
- 本地反向转发的服务端口被占用时，设备端测试启动应有清晰的占用报告并可配置其他端口。
- 注入的 CA 内容损坏（截断/非法文本）时，必须在请求前置校验阶段拒绝，错误类型与其余平台一致。
- 推送中断（数据线拔出）时不应残留半传输文件的错误引用，重试推送可恢复。
- 网络权限受限的模拟器场景下，设备端程序的失败信息应指向连网问题而非误导性的证书问题。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 库 MUST 在 Android 平台支持经由现有公共接口发起 HTTPS 请求，行为（默认校验、自定义 CA 内存与文件双形态、mTLS、SNI 覆盖、跳过校验）与已验收的主机平台语义一致。
- **FR-002**: 公共接口 MUST 保持平台无关：为达成 Android HTTPS 支持而引入的实现细节不得出现在公共头文件中，已有调用代码无须修改。
- **FR-003**: 由于 Android 平台默认不提供可供传统传输层直接读取的系统信任库形态，库 MUST 提供（或明确文档化）在 Android 上建立信任锚的途径：使用者可通过既有"注入 CA"能力完成信任建立。
- **FR-004**: 构建系统 MUST 提供单一入口的 Android 构建目标，覆盖至少 arm64-v8a 架构，自动准备所需的第三方传输层及其加密后端（含源码获取与交叉编译），不需要使用者手动下载放置。
- **FR-005**: 构建产物 MUST 包含可在设备端独立运行的集成测试与演示程序，其验证内容与主机侧等价（HTTP 基础流 + HTTPS/证书流）。
- **FR-006**: Makefile MUST 新增 `push` 目标：将最新构建产物推送到目标设备的约定私有目录，无已连接设备时报错并给出排查指引。
- **FR-007**: Makefile MUST 新增 `run` 目标：在目标设备上启动指定程序，把 stdout/stderr 实时转发到本机终端，并把远端退出码透传为本机命令退出码。
- **FR-008**: push/run 目标 MUST 支持多设备选择（显式序号优先；未指定且存在多台设备时列出候选并终止）；支持通过变量覆盖目标设备、端口与产物名。
- **FR-009**: 设备端集成测试 MUST 默认依托本地测试服务配合端口反向转发完成，公网可达性不属于硬依赖（可选的外部连通性用例除外）。
- **FR-010**: 既有五平台验收矩阵 MUST 更新：Android 行由"配置就绪待验证"变为有实际通过的构建/测试证据；不影响 macOS/Linux 既有分支的行为。
- **FR-011**: 工具链与文档 MUST 说明 Android 上的差异点（信任锚注入方式、系统 CA 的缺省缺失），并保持与项目架构决策记录一致。

### Key Entities

不涉及持久化数据域。核心工作对象为：**构建产物**（各架构的库与设备端可执行程序）、**目标设备清单**（由平台工具枚举的连接设备）、**本地测试服务与转发通道**（供设备端访问的自签 HTTPS 服务）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在真实 Android 设备上，四类 HTTPS 场景（默认拒、CA 注入通过、mTLS 通过、跳过校验通过）全部通过，且错误信息与主机平台同类场景一致。
- **SC-002**: 从全新克隆到产出 Android 库与设备端测试程序的全过程不需要人工介入步骤之外的手工操作，遵循文档首次完成不超过 30 分钟（不含一次性平台工具下载）。
- **SC-003**: 已完成首次构建的环境中，改一行代码后的「构建 + push + run + 出结果」闭环耗时不超过 2 分钟。
- **SC-004**: 使用本库的示例代码在 Android 上零修改编译运行（无平台相关开关或分支）。
- **SC-005**: 断开设备、多设备未指定、端口冲突三类异常场景均在 5 秒内给出明确错误与下一步指引。

## Assumptions

- 验证环境为真实设备或官方模拟器之一即可开始；US1/US3 的最终验收以真实设备为准。
- 支持的最低系统版本取业界常规基线（Android 7.0 / API 24 及以上），更低版本不在范围内。
- 设备端不需要 root 权限；所有文件落在应用/shell 可写的私有目录。
- 「make push&run 等」中的"等"涵盖为支撑该闭环所需的伴随目标（如清理设备旧产物、选择架构），范围以服务日常回归为限，不包含应用打包上架流程（APK/AAB 打包、签名发布等）。
- Android 的具体 TLS 后端选型（构建期决定，跟随 ADR-003"后端跟随平台"原则）属于规划阶段的实现决策，规格不预设具体方案，但约束：必须满足 FR-001 的行为一致性。
- 构建宿主按现有验收矩阵覆盖（macOS/Linux/Windows 宿主中先保证 macOS 宿主实测，其余宿主尽力兼容）。
